# DEYN Cloud Functions membership backend prototype

This package is isolated under `cloud-sync-lab`. It is not deployed and is not connected to the DEYN APK.

## Callable operations

- `createShop`: platform-admin-only provisioning after payment approval. It verifies the customer's Firebase UID and verified email, then creates the shop, owner membership and private user-shop index. It does not register a phone or return an owner token to the operator.
- `enrollOwnerDevice`: the primary owner signs in on their own phone and registers that phone after recent Firebase re-authentication. The backend returns a device-scoped custom token.
- `createWorkerInvitation`: an authenticated owner creates an email-bound, expiring, single-use invitation. Only a SHA-256 hash of the secret is stored.
- `redeemWorkerInvitation`: a verified-email worker redeems the invitation; one Firestore transaction consumes the invite and creates membership, device enrollment and the worker's private shop index.
- `issueDeviceSession`: returns a fresh device-specific Firebase custom token after checking shop, member and device status.
- `revokeDevice`: owner revokes one enrolled device.
- `revokeWorkerMembership`: owner disables a worker account for the shop; the member status immediately blocks all that worker's enrolled devices under Firestore rules.
- `updateShopSubscription`: platform administrator renews or changes expiry; every change creates a subscription audit record.

All callable endpoints require Firebase App Check. Firebase Authentication must be enabled. Owner and worker accounts must have verified emails.

## Device-specific session claims

A Firebase user's ordinary custom claims are global to that UID and cannot safely hold different device IDs for the same person using multiple phones. This prototype instead mints a Firebase custom token with per-session claims: `shopId`, `memberRole`, and `deviceId`. The same owner account can therefore use multiple phones without cloning IDs or overwriting the worker enrollment on a shared phone.

The client must sign in with each returned custom token and must never assign claims itself. Device IDs are random 128-bit values generated by the app and stored in native secure storage. App Check is an additional app-integrity gate, not proof that a client-supplied device ID is unspoofable.

## Trusted provisioning

The `platformAdmin` claim is assigned only by trusted Firebase Admin tooling, never by the customer app. Shop provisioning and subscription renewal are not public self-service operations. The owner cannot extend their own subscription by editing Firestore because client writes to the shop record are denied.

The guarded bootstrap utility is in `scripts/set-platform-admin.js`. It requires:
- Firebase Admin credentials available only in a trusted environment.
- The exact Firebase project ID.
- A verified email that matches the target UID.
- Explicit `DEYN_CONFIRM_ADMIN_CHANGE=YES`.

The operator provisions a shop for the customer's verified Firebase UID/email. The customer then signs in on their own phone, reads their own shop ID from `users/{uid}/shops`, and calls `enrollOwnerDevice`. The operator never receives the customer's owner session token.

## Transactional invitation safety

Invitation consumption, member creation, device registration and the private user-shop index update happen in one Firestore transaction. Concurrent redemption attempts are tested: only one can consume the invitation. The raw invitation secret is returned once and is never stored in Firestore. If custom-token minting fails after the transaction commits, the already-enrolled device can request a new session through `issueDeviceSession`; the invitation does not need to be reused.

## Automated test coverage

The current workflow runs:
- 116 JavaScript logic and legacy-migration tests.
- 16 Firestore Security Rules tests against the Firebase Emulator.
- 15 backend membership-service tests against the Firestore Emulator.

The backend tests cover shop provisioning without leaking an owner token to the operator, owner device enrollment/recovery, worker invitation and concurrent replay rejection, verified owner email, worker/device revocation, device session issuance and audited subscription renewal.

## Deployment requirements and limitations

Before deployment, configure a Firebase project, Authentication providers, Firestore, App Check, Cloud Functions billing/region and the app's Firebase configuration. The manual deployment workflow requires GitHub Actions secrets `FIREBASE_PROJECT_ID` and `FIREBASE_SERVICE_ACCOUNT_JSON`. Never commit service-account keys or secrets.

This remains a backend prototype. It does not implement payment-provider integration, automated subscription billing, account deletion, or the app-side custom-token sign-in and native Firestore bridge. No real shop data is transmitted.
